# Continuous verification

`.github/workflows/android.yml` runs on pushes to main, pull requests and manual dispatch. It uses Ubuntu 24.04, Temurin Java 25, Python 3.12, the checked-in Gradle 9.6 wrapper, Android platform `android-37.0` and build tools 36.0.0. JVM output remains Java 17. Actions are pinned to immutable commits; the Gradle action validates the wrapper and uses its basic cache. Pull requests can read the main cache but cannot write it.

The job downloads the four public 1.4.0 food-pack/report fixtures into runner temporary storage and verifies pinned SHA-256 values before tests. Missing downloads or changed bytes fail the job. `FORGE_TEST_PACK_DIR` enables the real catalog-artifact tests instead of skipping them. It then runs all Python importer tests and the complete host unit/Robolectric suite, Android lint, debug build and optimized **unsigned** release build. Test/build failures fail the workflow; `--continue` collects independent Gradle task results without changing its failing exit status.

The workflow has only `contents: read` permission, no signing credentials, no release publication and no signed artifact uploads. Gradle dependency submission and build-scan publication are disabled. Cancelling an older workflow run does not change the new run's result.

Release builds now fail without complete production signing settings. CI deliberately supplies `-Pforge.allowUnsignedRelease=true` to build an optimized unsigned APK; it must not provide any production signing inputs. Partial, mixed or invalid signing settings are rejected, including in unsigned mode. Standard Android debug signing remains independent and unchanged.

For a local production build, keep a PKCS12 keystore and a Java properties file outside the repository. Set `FORGE_RELEASE_SIGNING_PROPERTIES` to that file, containing `storeFile`, `storePassword`, `keyAlias` and `keyPassword`. A relative `storeFile` is resolved against that private file's directory; use forward slashes or escaped backslashes in Java properties. Alternatively supply all four environment variables: `FORGE_RELEASE_STORE_FILE`, `FORGE_RELEASE_STORE_PASSWORD`, `FORGE_RELEASE_KEY_ALIAS`, `FORGE_RELEASE_KEY_PASSWORD`. Do not mix both sources or put passwords in command-line arguments. `tools/release/build-production.ps1` accepts only the private properties path, disables Gradle configuration caching and runs `:app:assembleRelease`; it does not generate keys, create backups or publish anything. Additional logging/Gradle flags are rejected. Do not use verbose/debug build logging for signing. Release signatures use v2/v3, with v1/v4 disabled, and never fall back to the debug identity. The release guard rejects the standard debug alias, the known previous development certificate, or a certificate matching the machine's configured debug identity. Confirm the APK's public certificate fingerprint and the owner-controlled key/password backups before publishing.

The workflow passed local actionlint and equivalent Windows verification. Publishing requires a successful hosted run of the exact release commit; its run URL and result are recorded in the GitHub release notes. Local results and the production-signed emulator checks are listed in [1.4.2 production verification](release-1.4.2.md).

## Separate Android verification

Instrumented tests are not included in the hosted job: the updater's real in-place upgrade requires the existing private distribution certificate and explicit Android installer approval. No certificate belongs on a pull-request runner. On a local disposable emulator:

1. Use Android Studio to start an isolated API 37 AVD. Use an Android 8.0/API 26 AVD as an additional compatibility check when available. Preserve other emulators and personal data.
2. Run `adb devices`, select the QA serial through `ANDROID_SERIAL`, then run `./gradlew :app:connectedDebugAndroidTest`. The test application uses an isolated in-memory repository and its own temporary update directory.
3. Separately install the published previous APK, seed synthetic workouts, nutrition and an optional food pack, and export a backup. Record data and catalog counts before upgrading.
4. For a **published** newer compatible release, use Forge's real Download & Install UI. Check progress, Cancel/Retry, rotation, source permission denial/grant, installer Cancel/Retry, background process death and missing/corrupted download failures. Approve Android's installation; never install through ADB for this acceptance step.
5. Start the upgraded app normally. Verify the new version, unchanged workout/nutrition snapshots and usable offline catalogs. Observe that the dedicated private update directory contains zero files/bytes without invoking cleanup from the test observer. Verify the installed version is no longer offered.

Published 1.4.1 does not contain this downloader and uses a different development signing identity. Its users must follow the [verified backup/reinstall/restore migration](signing.md) to production 1.4.2; a browser download does not make those signatures compatible. Production-to-production updater acceptance uses a separately identified same-ID/same-production-certificate QA bootstrap with controlled future-release metadata/transport, followed by genuine optimized future-candidate installation through Android. The genuine candidate must contain no QA hooks. This establishes installer/data/cleanup behavior; a separate live GitHub download checks actual API/CDN transport. It does not establish an unpublished public release download. Temporary future candidates and bootstrap APKs must never be published.
