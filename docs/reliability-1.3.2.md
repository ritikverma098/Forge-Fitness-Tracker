# Forge 1.3.2 reliability verification

Base: `25a3230aa36037aeadca0dac28a319a02a6119ea` (1.3.1). Findings refer to the supplied independent audit, not additional feature requests. This report accompanies the 1.3.2 release. Existing Room schema 4 and portable backup format 3 remain unchanged.

## F-01 — workout drafts across writer recreation

Audit references at the base commit: `SetRow.kt:132–160`, `WorkoutViewModel.kt:21–48,299–309`, with the Finish gate in `ForgeApp.kt:213`.

**Reproduction:** combined actual Compose saved-state restoration, a fresh `WorkoutViewModel` and real Room. An injected failed 60→80 kg write restored 80 while the old writer's failure queue disappeared; the new writer allowed Finish with 60 persisted. Changed-unit and tiny canonical-weight cases also failed. Equivalent workout-name, workout-note and exercise-note cases were confirmed before correcting them. Same-writer retry controls passed.

**Correction:** save pending idempotent assignments, their exact canonical values, base values and revision acknowledgements in the writer's `SavedStateHandle`. Recover them before the save/Finish barrier can succeed. Already-persisted assignments are acknowledged without replay; conflicting or unknown bases require explicit review/Retry. Structural operations are never replayed. Scope restored editor text to its writer session and entity, and initialize a new editor from recovered/acknowledged state or Room. Preserve exact kg anchors and historical whitespace in notes.

**Host verification:** 84 focused recovery/state/performance tests passed, plus 37 backup/navigation/repository/message regressions. A subsequent 57-test constructor/message gate, debug and instrumentation APK builds, and lint passed (no lint issues). A further helper-level regression confirmed that owner-only saved text accepted a different entity's text. Binding the payload to `(owner, entity ID)` corrected it; all six helper/real-text recovery tests and both APK builds passed afterward. Numeric rows already have stable set-ID lazy scopes; no speculative numeric identity change was made.

**Native verification:** isolated API-37 emulator package `com.forge.workout.f132qa`, using the production application, Room and preferences. The ordinary `com.forge.workout` package and its records were not cleared or replaced. A persistent SQLite fault rejected a real 60→80 kg edit. After HOME, the Activity reached STOPPED; Android `am kill` removed PID 5938 while retaining task 132. Selecting that workout's Recents card created PID 11707 in task 132. The UI still showed 80 and Retry; confirming Finish left the workout active. A separate persistent-database assertion verified 60 remained uncommitted. No application fatal exception or ANR appeared in the captured recovered-process Logcat.

The later one-shot instrumentation used to remove the fault restarted the target and removed the saved task. Consequently the final native 80 kg / 640 kg-volume completion used a freshly entered 80; it is a normal save/Finish check, **not** evidence of in-place Retry after fault removal. Exact recovery-and-success behavior is covered by the host integration regressions. Screenshots, task/PID records, test XML and logs are retained outside the published project under the workspace's `work/reliability-1.3.2` directory.

Physical-phone/OEM process management and scrolling feel still require device verification. Emulator process recovery is not a physical-device performance benchmark.

## F-02 — branded nutrient reference units

**Reproduction:** audit references `tools/catalog/import_usda.py:47–56,99–126` at the base commit. The official FDC 2598460 response and the shipped record both contain energy 40; the source basis is 100 mL with a 250 mL / 100 kcal label, while the shipped record declared 100 g. Python regressions additionally confirmed missing branded units were silently accepted and unsupported mass portions could be offered. Three methods / 15 assertions or subtests failed before correction. The documented USDA basis rule was verified against the primary [branded-data documentation](https://fdc.nal.usda.gov/GBFPD_Documentation/).

**Correction:** branded imports require supported source unit metadata and preserve native grams or mL. No density or mass conversion is invented. All 200 exact branded source IDs were retrieved through the documented full-record API, and only serving-size/unit/household metadata was added to the original abridged inputs. The regenerated `2026-10-31` pack retains all 13,324 IDs, names, brands and 993,304 nutrient values. Fourteen foods now have a 100 mL basis; 189 label portions were added, giving 36,331 portions. Payload SHA-256: `af71a9e8015dbebd7be19c2f9fcee68c22746c10cc0dcc1bbc776071f1c7fabc`.

Initialization previously preserved even the specifically known old bundle as if it were a user-selected different revision; a real-Room regression failed before the policy fix. Only the retired bundled SHA is now upgraded. Arbitrary different explicitly imported revisions retain their existing preservation behavior. Catalog writes retain reference row IDs and do not rewrite frozen diary/recipe snapshots, personal foods or favorites.

**Verification:** 10 Python tests and an independent source-to-pack comparison passed. All 30 focused Kotlin cases passed: bundled initialization/upgrade (4), streaming catalog imports (10), nutrition migration (1), nutrition backup repository (7), and nutrition backup codec (8). Debug and instrumentation APKs built; lint reported no issues.

On the isolated API-37 emulator, the complete original catalog was installed, a gram-based diary and recipe were frozen, and initialization upgraded to the corrected pack. Android's JUnit runner reported one test / zero failures: stable juice row ID, mL-only conversion, 250 mL / 100 kcal, unchanged personal nutrition and all workout tables, idempotent reinitialization, and zero foreign-key violations. This large debug-device test exceeded the driver's original three-minute limit; the Android test continued and its final JUnit result was captured from Logcat. A separate fresh-process read-only assertion then passed through the normal instrumentation result channel, confirming the persisted correction, historical snapshots and completed F-01 workout.

The actual food picker displayed the corrected `100 ml` reference. Both the 250 mL label and manually entered 250 mL showed 100 kcal, with no gram option. Logging through the UI succeeded and the Nutrition dashboard showed 100 kcal. Screenshots and XML were captured, and the food-logging process Logcat had no app fatal exception or ANR. No ordinary Forge app data was changed.

## F-05 — automatic-backup contract

The audit's `backup_rules.xml:1`, `data_extraction_rules.xml:2` and `AndroidManifest.xml:9–11` still included the entire catalog-bearing database. The corrected catalog allocated **103,657,472 SQLite bytes** in the focused preflight, exceeding Android's documented [25 MB cloud quota](https://developer.android.com/identity/data/autobackup). A cloud transport is registered on the emulator, but Backup Manager is disabled and an explicit request returned `Backup is not allowed`. A cloud quota failure/restore was therefore **not** reproduced, and global backup/account settings were not changed.

The focused update chooses an explicit **local-only backup contract**: the manifest opts out, and both XML generations exclude persistent app storage, including device transfer. Settings and README direct users to portable local files. This avoids adding a new backup agent or cloud behavior. Existing files, Room schema and portable format remain unchanged.

Four policy regressions failed before correction; the local document control and ten catalog tests passed. All 57 corrected policy/catalog/document/repository/UI/runtime/ViewModel cases passed; debug/test APK builds and lint passed. The API-37 native check verified the installed opt-out flag, actual local resolver file write/read, and two complete restores into a disposable database without duplicates or foreign-key violations. Existing persistent QA records stayed unchanged. This verifies file I/O, not a new UI picker/cloud transport round-trip. Settings copy/buttons were inspected in the running app and screenshots captured; its process Logcat had no fatal exception or ANR.

## R-01 — background completion under write contention (confirmed)

The audit described this as a risk at `RestAlarmReceiver.kt:37–49` and `CatalogPackInstaller.kt:183–240`. Targeted investigation confirmed a more specific cancellation failure. The actual receiver's eight-second timeout cancels a blocked Room consumption call; SQLite later clears the deadline when the writer unlocks, but cancellation prevents the completion feedback. Retrying only when the deadline is still present would not repair this case.

The corrected host probe observed receiver completion at 9,249 ms after a 9.2-second writer hold, a null deadline and zero notifications/retries. Its correctness assertion failed. An earlier host probe incorrectly waited for receiver completion while holding the writer; its harness timeout is retained separately and is not defect evidence.

The API-37 reproduction used a fresh isolated package, granted notification/exact-alarm access, no resumed Activity, a real AlarmManager deadline and the production on-disk Room graph. Holding the writer through deadline +12 seconds produced the receiver timeout, then a null deadline and zero notifications. The correct-behavior assertion failed in 22.448 seconds. The failed workout was subsequently finished through the real UI and retained in history; no records were cleared.

**Correction:** the coordinator owns an in-flight delivery independently of the receiver or foreground ticker's await. The receiver retains its eight-second budget; failed/timed-out waits schedule a separately identified bounded retry of the original deadline. Retries are limited to twelve attempts and a three-minute original-deadline window; the application-owned claim is also time-bounded. Original deadline checks and Room's single-winner consume remain authoritative. Exact-alarm access is checked, with the existing inexact fallback when unavailable; strict Doze/OEM timing is not guaranteed by that fallback. No new service, permission, Room schema or portable-format change is required.

The same cancellation defect was reproduced when leaving the foreground while its expiry claim waited on Room. The shared coordinator fix covers both callers. All 138 focused cases in 14 suites passed, including real-WAL contention, foreground/background transitions, late-resume suppression, retry limits, denied exact-alarm access, timer-adjustment races, workout-draft recovery and backup regressions. Both APKs built and lint reported no issues. Independent source review found no blocker.

The unchanged real-alarm API-37 contention reproduction then passed in 14.373 seconds: despite the same receiver timeout, the original deadline was consumed and exactly one completion notification appeared after the writer released. Its owned QA workouts were finished through the real UI and retained.

The process-death check also passed. After observing the queued retry, automation killed only isolated QA PID 2506 with SIGKILL while its writer transaction was still open. The package remained `stopped=false`; the retry survived and Android cold-started PID 7538, posting the completion without an Activity launch. A read-only instrumentation attachment preserved that PID and passed: original deadline consumed, exactly one notification with the original timestamp, original 60 kg × 8 set intact, uncommitted writer metadata rolled back, and no duplicate notification after re-delivery/resume. Test-tool precondition/parser failures from earlier no-kill attempts are retained separately and are not counted as application failures or passes.

After R-02 added the shared startup gate, this actual process-death regression was repeated on the final functional v7 code: SIGKILL PID 28058, surviving OS retry, cold-start PID 32329 without an Activity launch, and a passing read-only same-PID verification (0.052 seconds). The original deadline was consumed, one notification retained its original timestamp, the 60 kg × 8 set was intact, the killed writer rolled back, and duplicate alarm/resume did not repost. Scoped Logcat had no fatal exception, ANR, restore or SQLite error. The earlier owned workout was finished through the UI and retained; the new QA fixture remains isolated from ordinary Forge records.

## R-02 — cross-store restore recovery (confirmed)

The audit references `BackupViewModel.kt:95–108` and `RoomBackupRepository.kt:100–101`. The same ordering remained: DataStore replacement completed before Room committed, and the ViewModel compensated only while its process survived. The focused real-Room/DataStore host regression produced one safety failure and one passing committed-restore control: bypassing in-process exception compensation left the original records with imported preferences after reopening. This host fault model is not an Android process-kill claim.

The API-37 native baseline independently confirmed the defect: after a completed settings write and before Room commit, a guarded SIGKILL removed only isolated QA PID 5494. Normal cold launch created PID 5754; the package remained `stopped=false`. Its complete workout/routine/nutrition/metadata graph matched the original generation exactly, but DataStore retained imported Light/lb/30-second/no-confirmation preferences. The coherent-generation assertion failed, with zero foreign-key violations. No committed records were lost and no ordinary Forge data was cleared. Original/imported snapshots, PID records, logs and expected assertion failure are retained.

**Correction:** the production backup repository coordinates settings and Room restoration. Before the existing transaction, it commits the previous settings into a small internal metadata journal. A successful transaction atomically removes that journal with the restored metadata; rollback or process death retains it. Recovery writes the previous settings before deleting its instructions. Failed recovery retains the journal and offers Retry. One operation mutex serializes restore, recovery and export, with caller collections frozen before waiting. Internal instructions are rejected on import and excluded from portable files.

Application startup, the main Compose graph, foreground timer activation and alarm delivery share the same recovery barrier. Ordinary successful restore keeps its existing navigation reset behavior; a failed settings recovery gates use until retry succeeds. Existing Room schema 4, migration chain and portable formats are unchanged. No new permission or dependency is needed.

All 76 focused cases in 11 suites passed, including ten real-Room crash/failure/concurrency cases, three shared-startup cases, actual Compose loading/error/retry wiring, existing restore/navigation/codec tests and F-04 validation. Debug/test APKs built and lint reported no issues. The initial build failure was stale task-local QA resource output, corrected through forced task regeneration; no app compilation failure was hidden. QA builds now use a separate per-package project cache.

The unchanged native crash regression then passed: SIGKILL removed PID 15436 inside the same pre-commit window; normal cold launch created PID 15868 with `stopped=false`. Before any instrumentation/snapshot access, actual Home and Settings rendered and selected Dark/Kilograms/90 seconds, proving startup recovery rather than an export fallback. The full original workout/routine/nutrition/metadata graph and original preferences matched exactly, including earlier baseline records; foreign-key violations were zero. Screenshots, original/imported snapshots, PID records and logs were retained. An additional test-only paused-coordinator/Retry regression is included in the final full-suite gate.
